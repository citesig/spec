# CiteSig v0.1 (draft)

**Status:** Draft — Request for Comment.
**Date:** 2026-09-03.
**Editor:** DeepInquiry.
**Feedback:** Open an issue at [github.com/citesig/spec](https://github.com/citesig/spec).

This document specifies the CiteSig protocol for attaching cryptographic verification signatures to factual claims. It is intended for implementers of language models, publishers, fact-checking services, and content platforms.

## 1. Terminology

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they appear in all capitals.

Additional terms:

- **Claim** — a natural-language factual statement, e.g. "The Great Barrier Reef is approximately 2,300 km long."
- **Attestation** — a signed data structure asserting that a signer stands behind a specific claim, backed by specific sources, at a specific time.
- **Signer** — the entity whose private key produces the signature. Identified by a public key or a public-key-derived identifier.
- **Source** — a URL, DOI, or other stable identifier for evidence supporting the claim. Sources are not signed by CiteSig; CiteSig signs their identifiers.
- **Verifier** — any party that receives an attestation and checks its signature against the signer's public key.

## 2. Design principles

CiteSig is designed against five constraints. These are non-negotiable properties of v1.0 and every design decision below can be traced to them.

1. **Offline verification.** A verifier MUST be able to check any attestation without network access, given only the attestation, the signer's public key, and standard cryptographic primitives.
2. **Portable representation.** An attestation MUST survive being copied as plain text through email, chat, LLM context windows, and non-preserving JSON re-serializers.
3. **Cryptographic neutrality about the claim.** A valid signature attests that the signer stands behind the claim with the listed sources at the listed time. It does not attest that the claim is factually correct.
4. **Small footprint.** A minimal attestation over a 500-character claim with two sources SHOULD serialize to under 1 KB in the compact form.
5. **Boring cryptography.** CiteSig uses primitives with production-grade library support across at least JavaScript, Python, Go, and Rust: EdDSA over Ed25519 for signatures, SHA-256 for hashing, and JCS (RFC 8785) for canonicalization.

Non-goals: consensus, blockchain, reputation scoring, source ranking, real-time trust networks.

## 3. Attestation data model

An **attestation** is a JSON object with the following fields. All fields listed as REQUIRED **MUST** be present.

```
{
  "v": "citesig/0.1",
  "claim": "<string>",
  "signer": "<did:key or https URL>",
  "sources": [ { "url": "<string>", "hash": "<string>" }, ... ],
  "issued_at": "<RFC 3339 timestamp>",
  "sig": "<base64url-encoded signature>"
}
```

### 3.1 Field definitions

- **`v`** (string, REQUIRED). Protocol version literal. For this draft, exactly the string `"citesig/0.1"`. Verifiers **MUST** reject attestations with an unrecognized `v`.

- **`claim`** (string, REQUIRED). The exact natural-language claim being attested. Whitespace within the string is significant. The claim **MUST NOT** exceed 4 096 UTF-8 bytes. Longer factual assertions **SHOULD** be split into multiple attestations.

- **`signer`** (string, REQUIRED). The signer's public identity. **MUST** be one of:
  - A [`did:key`](https://w3c-ccg.github.io/did-method-key/) identifier (recommended for offline-only workflows).
  - An `https://` URL where the signer publishes a [DID Document](https://www.w3.org/TR/did-core/) or a `.well-known/citesig.json` file exposing their current public key (recommended for organizations with rotating keys).

  Verifiers **MUST** treat the `signer` value as opaque for signature verification purposes: the public key used to verify `sig` is derived from `signer` per §5, and the signer string itself is part of the signed content.

- **`sources`** (array, REQUIRED, MAY be empty). Ordered list of evidence identifiers. Each element is an object with:
  - **`url`** (string, REQUIRED) — a URL, DOI (as `doi:10.xxxx/yyyy`), or other stable identifier for the source.
  - **`hash`** (string, OPTIONAL) — a `sha256:` prefixed hex digest of the source's canonical representation as retrieved by the signer. Recommended when the source is not immutable at its URL.

  A CiteSig attestation with an empty `sources` array is valid but weak: it attests that the signer stands behind the claim without pointing at evidence. Consumers **SHOULD** treat empty-sources attestations with additional scrutiny.

- **`issued_at`** (string, REQUIRED). The moment at which the attestation was signed, formatted per [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339) with UTC offset (e.g. `2026-09-03T20:41:00Z`). Verifiers **MUST** accept any well-formed timestamp; policy about staleness is out of scope for v0.1.

- **`sig`** (string, REQUIRED). Base64url-encoded (RFC 4648 §5, no padding) EdDSA-Ed25519 signature over the canonical serialization of the attestation with `sig` removed. See §5.

### 3.2 Extension fields

Implementations **MAY** add additional top-level fields for application-specific metadata, provided their names contain a colon (e.g. `deepinquiry:tier`, `myapp:confidence`). Verifiers **MUST** include unknown extension fields in the signed content per §5, so that an attestation cannot be silently modified after signing.

Field names without a colon are reserved for future versions of this specification.

## 4. Canonical serialization

To sign or verify an attestation, both parties **MUST** derive the exact same byte sequence from its JSON representation. CiteSig uses [JSON Canonicalization Scheme (JCS, RFC 8785)](https://www.rfc-editor.org/rfc/rfc8785):

1. Remove the `sig` field from the attestation object.
2. Serialize the remaining object with JCS: object keys sorted lexicographically, no insignificant whitespace, numbers in shortest round-trip form, strings escaped per JSON spec.
3. Encode the result as UTF-8.

The resulting byte sequence is the **signing input**. It is what the signer signs and what the verifier verifies.

Rationale: JCS is deterministic across implementations and languages, has multiple production libraries, and does not require the parties to preserve JSON key order or whitespace in transit. Alternatives considered — including detached JWS, COSE, and RFC 8785 with a custom canonicalizer — added dependencies without proportional benefit for this use case.

## 5. Signing and verification

### 5.1 Key material

The signer's public key **MUST** be an Ed25519 verification key (RFC 8032). Two `signer` formats are supported:

- **`did:key:z...`** — the public key is directly embedded in the identifier per the `did:key` method. Verifiers extract the key by decoding the multibase-multicodec suffix. No network access is required.
- **`https://<domain>/...`** — the signer identifier is a URL. To obtain the public key offline, the verifier **MUST** have previously cached the signer's key material or **MUST** treat the attestation as unverifiable. To obtain it online, the verifier fetches the URL, expects one of:
  - a JSON document at `<url>/.well-known/citesig.json` with a `keys` array of `{ "kid", "alg": "EdDSA", "crv": "Ed25519", "x": "<base64url>" }` entries, or
  - a W3C DID Document at `<url>` with a `verificationMethod` of type `Ed25519VerificationKey2020` or `Ed25519VerificationKey2018`.

Multiple active keys per signer are permitted; the signature carries no key hint, so verifiers try each active key until one succeeds.

### 5.2 Signing algorithm

To produce a valid attestation:

1. Construct the attestation JSON object with all REQUIRED fields except `sig`.
2. Compute the signing input per §4.
3. Sign the signing input with Ed25519, using the private key corresponding to a public key published under `signer`.
4. Base64url-encode the 64-byte signature (no padding).
5. Set `sig` to the encoded string.

The output attestation is the full JSON object with `sig` populated.

### 5.3 Verification algorithm

Given an attestation:

1. Verify that `v == "citesig/0.1"`; otherwise, **REJECT**.
2. Verify that all REQUIRED fields are present with correct types; otherwise, **REJECT**.
3. Extract `sig` and compute the signing input per §4.
4. Resolve `signer` to a set of one or more Ed25519 public keys per §5.1.
5. Attempt Ed25519 verification of the signing input against each public key. If any verifies, **ACCEPT**.
6. Otherwise, **REJECT**.

Acceptance means: the signer identified by `signer` produced the attestation, and the claim, sources, timestamp, and any extension fields have not been altered since. It does not mean the claim is true.

## 6. Compact form

For contexts where JSON is impractical — such as inline citations in prose, LLM output, or URL fragments — CiteSig defines a **compact form**:

```
citesig:0.1:<base64url(claim)>:<base64url(signer)>:<base64url(sourcedigest)>:<base64url(issued_at)>:<base64url(sig)>
```

Where `sourcedigest` is the SHA-256 hash (32 bytes) of the JCS canonicalization of the `sources` array. The compact form is **lossy for sources**: verifiers can confirm the signature but cannot enumerate sources without also receiving the JSON attestation. Compact form is primarily a discovery mechanism ("this text carries a CiteSig, ask its publisher for the full attestation"), not a full attestation.

The compact form **MUST NOT** be used as the sole distribution mechanism for factual claims where source enumeration matters.

## 7. Security considerations

- **Signature does not imply truth.** This point cannot be emphasized enough. A cryptographically valid CiteSig attestation only binds a signer to a claim + sources + timestamp. Consumers building trust decisions on top of CiteSig **MUST** layer signer reputation, source quality, and independent verification on top.

- **Replay is not addressed at the protocol layer.** The same attestation is valid forever unless the signer publishes revocation. Consumers who care about freshness **MUST** define their own staleness policy against `issued_at` and out-of-band revocation lists.

- **Key rotation.** The `signer` field intentionally does not embed a specific key. Signers rotating keys **SHOULD** keep old public keys published in their DID Document / `citesig.json` for a defined retention window so historical attestations remain verifiable.

- **Canonicalization attacks.** JCS is well-specified but implementations differ on edge cases (leading zeros in numbers, Unicode normalization, escaped surrogates). Test vectors in `test-vectors/v0.1/` cover the tricky cases. Implementers **MUST** pass all vectors before claiming CiteSig v0.1 conformance.

- **Extension field forgery.** Because unknown extensions are included in the signed content per §3.2, a malicious rewriter cannot add a `myapp:trust: high` extension without invalidating the signature. Verifiers displaying extension fields to users **SHOULD** clearly distinguish CiteSig-native fields (§3.1) from application extensions.

## 8. Open questions (not decided in v0.1)

The following are deliberately left unresolved for v0.1. Comment on the linked issues.

- **Revocation.** No revocation mechanism is defined. Signers may republish revocation lists at their signer URL, but no format is standardized. → issue #TBD
- **Multi-signer attestations.** Two signers backing the same claim is currently expressed as two separate attestations. A `co-signers` field or threshold-signature form may be added in v0.2. → issue #TBD
- **Fact identifiers.** No mechanism ties two attestations of the same claim to a stable fact-identifier. This is intentional — the claim string is the identifier — but implementers should note that near-duplicate claims are two different attestations. → issue #TBD
- **Content negotiation for signer URLs.** The Accept header contract for the online key-fetching flow is under-specified. → issue #TBD

## 9. Conformance

An implementation conforms to CiteSig v0.1 if it:

- Correctly produces attestations that pass every signing test vector in `test-vectors/v0.1/signatures.json`, given the same input and private key.
- Correctly accepts every well-formed valid attestation in the same file.
- Correctly rejects every deliberately-malformed or tampered attestation in the same file.
- Correctly canonicalizes every example in `test-vectors/v0.1/canonical.json`.

A conforming implementation **MUST NOT** advertise support for a later CiteSig version unless it also passes that version's vectors.
